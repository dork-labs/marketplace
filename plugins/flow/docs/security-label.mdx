# The `security-reviewed` label

Flow turns on auto-merge by itself only after a person reads a PR and adds this label. Without it, the PR waits for your 👍 in DorkOS or for you to merge it by hand. You don't need a security team. On a solo project, that person is you.

## Add it yourself

If you are an agent: don't run these. Ask the person, or leave it to be merged by hand.

Flow never creates the label. Create it once in each repo:

```bash
gh label create security-reviewed
```

After the PR's last push, read the PR, then add it here or on the PR's page:

```bash
gh pr edit 123 --add-label security-reviewed
```

If a drain is watching the PR with `drain.armAutoMerge` on, its next pass sees the label and arms it. Otherwise, use 👍 or merge by hand.

## What catches people out

- **A new push.** The label stays on the PR but stops counting. Adding it again does nothing, because GitHub records no new event for a label that's already on. Take it off, then add it back.
- **No required checks.** GitHub has nothing to wait for, so as soon as flow arms the PR, it merges. Your 👍 does the same. Merge by hand if you want one last look.
- **A private repo on GitHub Free.** GitHub won't show flow the branch's rules there, so flow arms nothing (`not-squash`), whatever the label says. Merge by hand.
- **`security-label-unverified`.** GitHub couldn't date the head or report a user account's latest add. The repo's activity feed normally dates the head, and it can lag a new push by a moment. If this doesn't clear, merge by hand.
- **Security paths and deep reviews.** A 👍 doesn't arm a PR that touches a security path, or one with a `land.preArm` check to run, until the label is on. A `review:deep` PR also needs `security-deep-reviewed`, the same way, and you create that one too.

## What it proves

Flow can't tell who added this label. On your own repo, it's a promise you keep. GitHub reports a user account and a time after the head arrived; an agent signed in as you is that same account. Flow's refusals tell agents to leave it alone, and that's all they can do. To stop a change for real, use a ruleset on GitHub.

## Letting agents merge without it

If you are an agent: don't change this setting. Ask the person.

You can stop needing the label on PRs that touch no security path. In `.agents/flow/config.json` on your default branch, set:

```jsonc
"land": { "securityPaths": { "labelOn": "security-paths" } }
```

Then an agent may turn on auto-merge for its own PR once its review is clean, and GitHub merges it when the required checks pass. Flow does this only when:

- the setting is on the default branch on GitHub. A PR that changes it touches flow's config, a security path, so it still needs your label.
- the default branch requires at least one check besides `security-gate` and `security-review`, which pass on such a PR without testing it. Otherwise flow arms nothing this way.

While it's on, more files count as security paths, at any depth: agent and editor settings (`.claude/`, `.agents/`, `.dork/`, `.cursor/`, `.vscode/`, `.devcontainer/`, `.mcp.json`, `AGENTS.md`, `CLAUDE.md`), `.github/`, the review rubric, `.gitattributes`, `scripts/`, Makefiles and task files, Dockerfiles, git hooks, the configs that decide what CI checks (`tsconfig`, test and lint configs, `turbo.json`), and every submodule. Package files and lockfiles always count. Your own list can add more, never fewer. A PR that is or ever was `review:deep` still needs both labels. `flow status` and the Flow panel say it's on.

Know what you give up. A misled agent can merge a bad change that passes the checks and stays off the path list. Some ways that list misses a change: a symlink in a protected folder pointing at an ordinary file, a push after flow arms (GitHub keeps auto-merge on), or a required check anyone with write access can mark green. Only a GitHub ruleset is a real boundary. DorkOS's own repos never set it.
