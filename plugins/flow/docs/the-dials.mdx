# The dials

`/flow` ships with sane defaults: the resolved set already runs the loop the way the charter intends. This page is the reference for when you want to change one. Every dial here is a real, validated field; nothing is aspirational.

## Where the dials live

Settings are split by who a change reaches:

| Where                             | Who it reaches                                       | What lives there                                                                                                            |
| --------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `.agents/flow/config.json`        | Everyone on the repo, once you commit it             | The engine contract: autonomy, eligibility, involvement, gates, review, loops, ingestion.                                   |
| `.agents/flow/config.local.json`  | Only this computer (kept out of git)                 | This machine's credentials, model bindings and overrides, such as whether flow starts work on its own and how much at once. |
| DorkOS, per project               | Only this computer, and only a person can change it  | [How much it does on its own](#how-much-it-does-on-its-own), how long an agent waits for you, the accounts it may use, the pause default. |
| Where the tick is scheduled       | This install                                         | How often the scheduled runs fire ([Cadence](#cadence-set-it-where-the-tick-is-scheduled)).                                 |

In DorkOS, each project's Flow settings (⚙ on the project's page, or Settings → Flow) show the two files as two boxes, **Shared with the repo** and **Just me**, and name the file a shared change writes. Saving changes only the keys you touched and checks the result before keeping it. flow never commits: a shared change reaches others once you commit it.

`config.schema.json` is generated from the Zod `FlowConfigSchema` in `@dorkos/flow` (`config-schema.ts`) via `z.toJSONSchema`. The schema is authoritative: an out-of-enum value or a violated floor fails to parse, so you cannot silently mis-configure the engine. Any field you leave out takes its default, so a config written by an older flow stays valid after an update. Edit `config.json`; the `$schema` reference gives you completion and validation in any schema-aware editor.

<Callout type="info">
  The v1 harness reads `.agents/flow/config.json` only. A per-repo `WORKFLOW.md` override is part of
  the config contract, but applying it is the promoted config loader's job (the deferred P5 server
  build), not the v1 skills. A `WORKFLOW.md` will not take effect yet.
</Callout>

<Callout type="warn">
  Some dials configure a typed contract whose continuous runner is the deferred P5 server. They are
  real and validated today, and the v1 harness honors them in prose (the Pulse tick walks the loops
  in priority order). What is **not** built is the always-on process that fires each loop on its own
  `intervalMs` unattended. Each such dial is flagged below.
</Callout>

## Cadence: set it where the tick is scheduled

flow ships three scheduled runs, all switched off until you approve them. Their timing in the plugin's files is the package's defaults:

| Scheduled run | What each run does                                                                  | Default cron                     | Default timezone      |
| ------------- | ----------------------------------------------------------------------------------- | -------------------------------- | --------------------- |
| `flow-drain`  | Claims the top-ranked ready item and carries it to its review gate.                 | `0 * * * *` (top of every hour)  | `America/Los_Angeles` |
| `flow-triage` | Readies or parks every untriaged item, and releases claims untouched for 7+ days.   | `0 8 * * *` (08:00 every day)    | `America/Los_Angeles` |
| `flow-groom`  | A read-only backlog health check (`/flow:groom check`). The full groom stays yours. | `0 9 * * 1` (09:00 every Monday) | `America/Los_Angeles` |

How often they actually fire is decided by whatever starts them, so that is where you change it:

- **With your own scheduler** (an OS `cron` line or a launchd job, a scheduled CI job, a poller): its own entry is the cadence. Change it there. That scheduler never reads flow's defaults, and a flow update never touches its entry. See [Bring your own scheduler](/docs/guides/flow/bring-your-own-scheduler).
- **On DorkOS**: change it on the **Schedules** page. Open `flow-drain` (or `flow-triage`, or `flow-groom`), choose **Edit**, and set a new time or timezone under **Schedule**. DorkOS keeps your timing for this install on its side, so the plugin's files stay as they shipped and a flow update never undoes it. The schedule stays approved, because you made the change yourself. Its row then says **Your timing**, and **Reset to the package's default** puts flow's own timing back. If an agent changes the timing instead, the schedule stops and waits for you to approve it. Never edit the `cron` line in the plugin's own file: an edit there is undone by the next update, and DorkOS asks you to approve the schedule again each time.
- **On a DorkOS release from before this change** (0.82 and earlier), a package's schedule can only be switched on or off there. To pick your own cadence on one of those, make the schedule your own: on the **Schedules** page, create a schedule for this project's agent whose prompt is `Run one /flow continue tick in this project, then stop.`, give it the cron you want and the limits flow ships (at most 2 hours, accepting edits), and leave `flow-drain` switched off on DorkOS so the tick does not run twice. Keep the prompt that short; do not copy the text of `flow-drain` into it, because that text finds flow's files relative to where it sits inside the plugin.

`/flow:status` shows the cadence each of this project's flow schedules uses on DorkOS, your own `/flow continue` schedule included. `/flow:pause` switches that one off too, and the pause flag stops it either way.

For reference, this is what the shipped `schedule:` block of `flow-drain` holds. The block is also what makes the file a scheduled task at all; remove it and the same file is a plain skill:

```yaml
---
name: flow-drain
description: Claim the top-ranked eligible issue and carry it to its review gate.
schedule:
  cron: '0 * * * *'
  timezone: America/Los_Angeles
  enabled: false
  max-runtime: 2h
  permissions: acceptEdits
---
```

| Field                  | What it does                                                              | Default                        | To change it                                                                  |
| ---------------------- | ------------------------------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------- |
| `schedule.enabled`     | The package's default switch: installing never arms the tick.             | `false`                        | Leave it. On DorkOS, approving the tick on the Schedules page switches it on. |
| `schedule.cron`        | When each tick fires (one tick claims and carries one issue to its gate). | `0 * * * *` (top of each hour) | Where the tick is scheduled (above), never in this file.                      |
| `schedule.timezone`    | The timezone the cron is evaluated in.                                    | `America/Los_Angeles`          | Where the tick is scheduled (above), never in this file.                      |
| `schedule.max-runtime` | Hard ceiling on a single tick.                                            | `2h`                           | The package's choice; an edit here is undone by the next update.              |
| `schedule.permissions` | The tool-permission posture for the unattended session.                   | `acceptEdits`                  | The package's choice; an edit here is undone by the next update.              |

<Callout type="warn">
  The tick ships `schedule.enabled: false`, so installing never arms it; the switch on DorkOS's
  **Schedules** page is the one that counts, and it outlasts updates. Autonomous mode needs a
  **running DorkOS server**; manual `/flow` does not.
</Callout>

## Autonomy

How aggressively the engine takes work, under `autonomy`:

| Dial                | What it does                                           | Default        | Notes                                                                 |
| ------------------- | ------------------------------------------------------ | -------------- | --------------------------------------------------------------------- |
| `default`           | Whether `/flow` runs to a gate or one stage at a time. | `"auto"`       | `"auto"` drains the ready queue; `"manual"` runs one stage and stops. |
| `concurrency`       | Sequential vs parallel item processing.                | `"sequential"` | v1 stays sequential (WIP-1). `"parallel"` is reserved for P5.         |
| `wipCap.global`     | Max items in flight across all projects.               | `2`            | The ceiling on total concurrent work.                                 |
| `wipCap.perProject` | Max items in flight per project.                       | `1`            | Keeps one project from monopolizing the loop.                         |
| `seat`              | Which autonomous runner hosts the loop.                | `"pulse"`      | `"pulse"` is the sole v1 seat; a generic `watcher` seat is planned.   |

<Callout type="info">
  `concurrency: "parallel"` parses, but the v1 harness runs the dispatch tick one item at a time
  (atomic multi-claim and fencing are deferred to P5). Leave it `"sequential"` until the server
  build lands.
</Callout>

## Eligibility

Dispatch only ever claims an item that is genuinely ready. That gate is the `agent/ready` label, produced at the shaping stages:

<Steps>
  <Step>
    **TRIAGE** applies `agent/ready` (and the `stage/*` label) when it accepts work, on both routes
    (simple to EXECUTE, complex to IDEATE).
  </Step>
  <Step>**DECOMPOSE** applies `agent/ready` to the execute-ready tasks it emits.</Step>
  <Step>
    **Dispatch** filters to ready items only, then ranks them. An empty queue with
    shapeable-but-not-ready work behind it reports "0 ready, N shapeable: run a triage pass?" rather
    than stopping silently.
  </Step>
</Steps>

`agent/ready` is a label the shaping stages produce, not a dial. What you _can_ tune is how the ready pool is ordered once it exists, under `dispatch`:

| Dial                 | What it does                                                      | Default                                                              |
| -------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------- |
| `dispatch.rank`      | The ordered ladder dispatch ranks eligible items by.              | `["unblockers", "priority", "projectStatus", "type", "size", "age"]` |
| `dispatch.sizeOrder` | Whether smaller or larger items are preferred at the `size` tier. | `"small-first"`                                                      |

Eligibility also removes non-dispatchable state, items with open blockers, items in completed or canceled projects, WIP-capped items, and items the `ownership` policy does not permit.

## Involvement

When the engine asks you versus proceeds on its own, under `involvement`:

| Dial                              | What it does                                                           | Default                                                                                 |
| --------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `comms`                           | Voice and channel-inference for how the engine talks to you.           | `"infer-from-trigger"`                                                                  |
| `calibration.proceedSilentlyWhen` | Conditions under which the engine acts without asking.                 | `["reversible", "confident"]`                                                           |
| `calibration.alwaysAsk`           | The non-trimmable floor: these are **always checked**, never silently. | `["irreversible-or-destructive", "outward-facing", "secrets-or-spend", "scope-change"]` |
| `calibration.stageBias.intake`    | Default posture during shaping stages.                                 | `"ask"`                                                                                 |
| `calibration.stageBias.execution` | Default posture during execution.                                      | `"proceed-and-log"`                                                                     |
| `nudge.relay`                     | Send an out-of-band Relay ping when a question parks.                  | `false`                                                                                 |
| `nudge.telegram`                  | Send an out-of-band Telegram ping when a question parks.               | `false`                                                                                 |

`comms: "infer-from-trigger"` is the key dial for tone: involvement is uncertainty-gated, not stage-gated. The engine reads the trigger (a live `/flow` session versus an unattended tick) and the calibration ladder, so IDEATE asks freely and EXECUTE asks rarely as an emergent property of one rule, not a per-stage switch.

<Callout type="warn">
  `calibration.alwaysAsk` is a **floor, not a preference**. The schema enforces at least one entry
  (`alwaysAsk: []` fails to parse), so autonomy can never be silently widened past the four
  irreversible-or-outward classes. You can add to the floor; you cannot empty it. Something on
  the floor is always checked: by you, or, if you choose, by the reviewer agent. Never by nobody,
  and a decision about secrets or spending always waits for you.
</Callout>

### How much it does on its own

Each project has one more dial, and it is not in any file in the repo: **Ask me first**, **Tell
me after** or **Just do it**, set in the project's Flow settings in DorkOS. It decides who answers
each kind of ask, so flow can run on its own without anything going unchecked.

| Kind of ask            | Ask me first  | Tell me after                                    | Just do it                              |
| ---------------------- | ------------- | ------------------------------------------------ | --------------------------------------- |
| Ship finished work     | asks you      | the reviewer agent approves, and you're told     | the reviewer agent approves             |
| Agent questions        | waits for you | the agent goes with its pick at the deadline     | the agent picks and writes down why     |
| Sort new ideas         | asks you      | every morning, and you're told                   | every morning                           |
| Retry and fix problems | asks you      | on its own, and you're told                      | on its own                              |

Whatever you pick, someone checks: you, the reviewer agent, or, for an ordinary question at Tell
me after, the agent's own pick once the wait is over (1 hour, 4 hours or end of day; 4 hours
unless you change it). Something on the floor is never settled by a deadline alone. **Customize**
sets one kind apart from the dial, and the dial then reads "Custom". After you answer an ask,
flow offers once to handle that kind on its own next time; yes changes only that kind, for that
project. What flow settled without asking shows in DorkOS's Activity as "While you were away".

It lives in DorkOS, not in `.agents/flow/`, because it decides who checks the agents, and an
agent can write any file in the checkout. Only a person can change it; with Require login off,
anyone on this computer can, and the setting says so. Flow reads a copy DorkOS keeps for it; with
nothing chosen yet, flow asks you first, except that failing checks are still fixed on their own as
they always were. `flow autonomy` shows what is in force. The reviewer agent only ships work when
`review.adversarial` is on and it recorded a clean review of the latest commit; without it, "Ship
finished work" stays at Ask me first.

The `nudge` flags are the only out-of-band attention channel. In shared-account mode (the common case, where there is no separate reviewer identity), a parked question's only durable signal is a tracker comment plus the `agent/needs-input` label; turning on `nudge.relay` or `nudge.telegram` promotes that to a real ping so a parked question is seen, not buried.

## Gates

The checkpoints between stages, under `gates`:

| Dial                                 | What it does                                                        | Default      | Notes                                                                           |
| ------------------------------------ | ------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------- |
| `planApproval`                       | Stop after DECOMPOSE for human sign-off before EXECUTE.             | `false`      | Off by default: the engine flows DECOMPOSE to EXECUTE. Turn on for a plan gate. |
| `review.requireCiGreen`              | Require green CI before the review gate clears.                     | `true`       | Part of the review gate, which is **always on**.                                |
| `review.reapproveOnFunctionalChange` | Re-request approval if the change shifts functionally after review. | `true`       | Keeps a stale approval from carrying a changed diff.                            |
| `circuitBreaker.estimateMultiplier`  | Trip the breaker when actual work exceeds the estimate by N times.  | `2`          | Lower to fail fast on runaway items.                                            |
| `circuitBreaker.tokenBudget`         | Hard token ceiling per item before the breaker trips.               | `2000000`    | Raise for genuinely large items; lower to cap spend.                            |
| `projectCompletion`                  | Whether DONE closes a finished project itself or recommends it.     | `"advisory"` | `"auto"` also needs an adapter supporting the optional `completeProject` verb.  |

<Callout type="info">
  The **review gate** (after VERIFY) is always checked and is not a dial: no field disables it.
  Who checks it is [How much it does on its own](#how-much-it-does-on-its-own). With
  `review.mergeOnApproval` on, an approval arms the approved commit to merge once checks pass.
</Callout>

`projectCompletion` is a ceiling, not a promise. On `"auto"`, DONE closes a project only when nothing inside it is still open, its progress is complete, no active spec points at it, and your adapter supports closing projects (an optional verb). Otherwise you get `"advisory"` plus a line saying which condition stopped it. The strictness is the point: a closed project hides every issue left open inside it from the work queue for good.

## Review

The adversarial review a branch faces **before** its PR is opened, under `review`:

| Dial          | What it does                                                        | Default       | Notes                                                                                                                                                |
| ------------- | ------------------------------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `adversarial` | Dispatch an independent reviewer on the branch before the PR opens. | `true`        | Turn off for a cheaper, lower-assurance loop.                                                                                                        |
| `rubric`      | Path to the rubric the reviewer reads.                              | `"REVIEW.md"` | Relative to the repo root (or the current directory outside a repo); absolute paths are used as-is. `/flow:init` scaffolds one if it does not exist. |
| `reviewers`   | How many independent reviewer agents each review dispatches.        | `1`           | Raise for a wide blast radius; each extra reviewer is another full diff read.                                                                        |

Three different things in this config are called "review", and they fire at three different moments. `review` (this block) is the **machine** review, before the PR exists. `gates.review` is the **auto-merge** ladder, after the gate is approved. `stages.review` is the **review gate** itself, which is always checked and has no off switch.

A reviewer gets the diff, the rubric, and the work item's intent — never the implementer's account of what it did. That is the whole point: an agent reviewing its own branch from its own working context reviews the story it remembers writing, not the code it produced. The rubric is what keeps the review calibrated (what counts as blocking, what CI already covers, how many nits are worth raising); without it the reviewer still runs on general discipline, so a missing rubric degrades the review rather than skipping it — and the run says which happened.

Raising `reviewers` above `1` pools findings rather than polling them: **any blocking finding blocks unless it is rebutted**, whoever else missed it.

## Context and resuming

How long a session lives, and how hard the engine tries to get back into the one that started the work, under `context`:

| Dial                | What it does                                                                     | Default             | Notes                                                                                |
| ------------------- | -------------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------ |
| `perIssue`          | Session lifetime per work item.                                                  | `"fresh-session"`   | `"sticky-session"` sends follow-ups and rework back to the session that started it.  |
| `perStage`          | Subagent lifetime per stage.                                                     | `"fresh-subagent"`  | A fresh subagent per stage keeps each stage's context clean.                         |
| `resume`            | How hard to try continuing the originating worker before starting a fresh one.   | `"prefer"`          | `"require"` stops rather than degrading; `"never"` always starts from the artifacts. |
| `compactionTrigger` | Fraction of the context window that triggers compaction.                         | `0.65`              | Lower it if long runs lose detail before compaction fires.                           |
| `stageBudgets.*`    | Per-stage token budgets (`specify`, `decompose`, `execute`, `verify`, `review`). | `40000`–`80000`     | EXECUTE gets the largest budget; REVIEW the smallest.                                |
| `externalize`       | The durable artifacts context is written out to.                                 | the three run files | These are what a fresh worker reads when it cannot continue the original.            |

`perIssue: "sticky-session"` and `resume` are two halves of one idea: continuing an agent's reasoning beats re-deriving it. Sticky sessions decide **where a follow-up goes**; `resume` decides **what happens when it cannot get there** (only the machine holding the transcript can continue a session).

<Callout type="warn">
  `resume: "require"` is a stop, not a preference. When the originating worker cannot be reached,
  the run says so loudly and halts, rather than quietly starting a fresh worker that has lost the
  reasoning. Use it when a silent restart would be worse than a paused item; leave it `"prefer"`
  otherwise.
</Callout>

## Models

Which model each delegated worker runs on, under `models`. The block is split across two files on purpose:

| Dial                   | What it does                                                             | Default       | Lives in            |
| ---------------------- | ------------------------------------------------------------------------ | ------------- | ------------------- |
| `tiers.implementation` | Tier for agents that write the change.                                   | `"workhorse"` | `config.json`       |
| `tiers.review`         | Tier for reviewer agents.                                                | `"workhorse"` | `config.json`       |
| `tiers.analysis`       | Tier for planning and analysis agents.                                   | `"workhorse"` | `config.json`       |
| `tiers.mechanical`     | Tier for searches, scaffolds, renames, and log triage.                   | `"fast"`      | `config.json`       |
| `bindings.workhorse`   | The real strong general-purpose model this machine's harness should use. | none          | `config.local.json` |
| `bindings.fast`        | The real cheap fast model this machine's harness should use.             | none          | `config.local.json` |

A tier is a role, not a model. `workhorse` means "the strong general-purpose model this machine can reach" and `fast` means "the cheap quick one" — and which models those actually are is a property of your machine, not of the repo, so the committed half names none and ships no binding. `/flow:init` asks you to rank what your harness can reach and writes the answer to the local file.

The judgment classes default to `workhorse` and mechanical work to `fast` for one reason: mechanical work has a checkable answer, so a cheap model that gets it wrong gets caught. A weak reviewer just misses things quietly.

There is a third tier the config deliberately cannot name: `frontier`, the model your orchestrating session is itself running on. Flow never selects it, which is why it is absent from the enum. What flow does insist on is that **every delegated worker names its model explicitly** — because on a harness that inherits the parent's model when you omit one, an orchestrator running at frontier that omits it runs every delegate at frontier cost, silently.

<Callout type="info">
  Nothing here fails closed. One model available? Bind both tiers to it and the policy becomes a
  no-op. No binding at all? The delegate falls back to your harness's own default model **and the
  run says so** — a silent fallback is indistinguishable from a policy that worked.
</Callout>

## Loops

The reconciler registry. Each loop is one reconciler; the map is the extension seam (add a loop by registering it, retire one with `enabled: false`). Every loop takes the same three dials, under `loops.<id>`:

- **`enabled`** — whether this reconciler runs.
- **`priority`** — lower number runs earlier in the tick and **wins same-item contention** (recovery before dispatch).
- **`intervalMs`** — how often the typed scheduler considers this reconciler due.

| Loop       | `priority` | `intervalMs`         | What it does                                                       |
| ---------- | ---------- | -------------------- | ------------------------------------------------------------------ |
| `recovery` | `10`       | `300000` (5 min)     | Adopt or restart orphaned `agent/claimed` work; runs first.        |
| `inbox`    | `20`       | `60000` (1 min)      | Poll for replies on parked `agent/needs-input` items; resume them. |
| `review`   | `25`       | `300000` (5 min)     | Evaluate the auto-merge ladder at the review gate.                 |
| `dispatch` | `30`       | `300000` (5 min)     | Claim the top-ranked eligible item and carry it to its gate.       |
| `triage`   | `40`       | `3600000` (1 hour)   | Classify and ready incoming work so dispatch never starves.        |
| `hygiene`  | `50`       | `21600000` (6 hours) | Housekeeping: surface starvation, reconcile stale records.         |

The priority order is deliberate: recovery first (never lose in-flight work), then inbox (a parked human is the cheapest unblock), then review and dispatch, with triage and hygiene as the slow background. To make the loop more responsive to replies, drop `loops.inbox.intervalMs`; to throttle tracker reads, raise it.

<Callout type="warn">
  In v1 the scheduled tick fires on its `cron` and walks the enabled loops in priority order. A
  runner that fires each loop on its own `intervalMs` is the deferred P5 server.
</Callout>

## Ingestion

How inbound tracker events reach the engine, under `ingestion`:

| Dial             | What it does                                               | Default         | Notes                                                      |
| ---------------- | ---------------------------------------------------------- | --------------- | ---------------------------------------------------------- |
| `producer`       | The inbound transport: poll the tracker or receive pushes. | `"poll"`        | `"webhook"` is reserved; the webhook producer is deferred. |
| `pollIntervalMs` | How often the polling transport reads the tracker.         | `60000` (1 min) | Lower for faster pickup; raise to reduce API load.         |

The producer is a swappable seam: the inbox reconciler consumes a normalized `TrackerEvent[]` from whichever transport is injected. v1 ships the `PollingTransport` (poll plus a durable watermark cursor); the webhook producer is a config-level drop-in once the inbound endpoint exists.

## Which dial should I touch?

| If you want to...                            | Turn this                                                                                      |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Turn the autonomous loop on                  | Approve `flow-drain` on the Schedules page, which switches it on (server required)             |
| Stop it for a while                          | `/flow:pause` (and `/flow:resume` to lift it)                                                  |
| Make the autonomous tick fire more often     | Change it where the tick is scheduled ([Cadence](#cadence-set-it-where-the-tick-is-scheduled)) |
| Run more than one item at a time             | Wait for P5; v1 is `autonomy.concurrency: "sequential"`                                        |
| Cap how much work is in flight               | `autonomy.wipCap.global` / `wipCap.perProject`                                                 |
| Get pinged when a question parks             | `involvement.nudge.relay` / `nudge.telegram`                                                   |
| Require sign-off on the plan before EXECUTE  | `gates.planApproval: true`                                                                     |
| Review a branch harder before the PR opens   | `review.reviewers` (raise it)                                                                  |
| Skip the pre-PR machine review entirely      | `review.adversarial: false`                                                                    |
| Cap spend per item                           | `gates.circuitBreaker.tokenBudget`                                                             |
| Make replies resume faster                   | `loops.inbox.intervalMs` (lower it)                                                            |
| Throttle tracker reads                       | `ingestion.pollIntervalMs` (raise it)                                                          |
| Turn a reconciler off                        | `loops.<id>.enabled: false`                                                                    |
| Reorder which reconciler wins contention     | `loops.<id>.priority`                                                                          |
| Send follow-ups back to the same session     | `context.perIssue: "sticky-session"`                                                           |
| Stop instead of restarting a lost session    | `context.resume: "require"`                                                                    |
| Point flow at this machine's models          | `models.bindings` in `config.local.json`                                                       |
| Run mechanical work on a stronger model      | `models.tiers.mechanical: "workhorse"`                                                         |
| Close a finished project without being asked | `gates.projectCompletion: "auto"`                                                              |
| Keep a bare label the groom audit flags      | List it in `groom.unnamespacedLabels`                                                          |
