# Build your tracker adapter

`/flow`'s engine never speaks to a tracker directly. The stage skills speak only the `WorkItem`
model and a fixed set of capability verbs; the single tracker-aware unit is an **adapter**. `/flow`
ships one adapter, for Linear. For any other tracker, or a different wiring of Linear, you generate
your own from the contract and prove it with a conformance test.

## The generate-and-verify loop

<Steps>
  <Step>
    **Choose your tracker and connection.** `/flow:init` asks this on first run.
  </Step>
  <Step>
    **Generate from the contract plus the closest reference.** The bundled references are
    Linear-MCP and Linear-Composio, so common cases are a small edit.
  </Step>
  <Step>
    **Run the conformance test until green.** A malformed adapter fails here instead of corrupting
    dispatch later.
  </Step>
  <Step>
    **Commit the adapter as your code.** `/flow:init` writes it to
    `.agents/flow/adapters/<tracker>/SKILL.md` in your project, so updating flow never touches it.
    It is the single audit surface for every tracker write.
  </Step>
</Steps>

## What the contract pins down

- **Five state categories.** States match on a _category_
  (`backlog | unstarted | started | completed | canceled`), never a display name.
- **Required `WorkItem` fields.** Every item carries what the stage skills and oracles read.
- **`blockedBy` resolution.** Dependency edges resolve, so the ranker can put unblockers first.
- **Label re-namespacing.** Your tracker's labels map onto `agent/*`, `stage/*` and the other
  families.

<Callout type="warn">
  The engine trusts the adapter; the conformance test earns that trust. Never wire an adapter that
  has not passed it.
</Callout>

## Add code so the `flow` command can use it

The `flow` command runs the mechanical steps (snapshot, claim, stage, done) and cannot read prose.
It needs an `adapter.ts` beside your `SKILL.md`. Without one the skill still works, and `flow` says
the adapter has no code.

- Export `CONTRACT_VERSION` (`"1.4.0"`) and `createAdapter(ctx)`. `ctx` holds your config, your
  secrets, a `transport` that runs your tracker's CLI with no shell, and `warn`. No flow imports
  needed.
- List the methods you implement in `capabilities`: `getCurrentUser`, `getBacklogSnapshot`,
  `getItem`, `applyWorkState`, `comment`. The contract's "The code realization" section defines
  each.
- A read that fails throws; it never returns an empty list.
- `applyWorkState` builds labels from a fresh read, never from the item it was handed, and never
  creates a label.
- `flow` re-reads the item after every write and stops with exit 4 if the change did not stick.

## Keeping it current

When the contract version changes, re-run `validate-adapter.ts`; if it fails, re-run the
`building-adapters` loop.
