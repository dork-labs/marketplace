# Draining in parallel

`flow drain --parallel 3` carries three ready items at once, each in its own worktree with a worker on the account with the most room. A separate reviewer session reads every push, and `flow pr` opens the PR only after a clean review at the branch head.

## Before you start

Allow each account flow may spend with `flow accounts set <id> --role rotation`. With none registered, sessions run on your own login. Each user judges their own use of more than one account against Anthropic's terms.

## Where sessions run

`--host` picks `cli` (plain `claude -p`), `cmux` or `dorkos`. `auto` takes cmux when the drain runs inside it, then DorkOS, then the CLI.

## What each line means

- `claimed on <account> (cli)`: a worker started.
- `moved to <account>`: an account ran out, so the work moved.
- `parked: <reason>`: a person is needed; the reason is posted on the item.

## What happens at a limit

Near a limit, the worker finishes its step, writes `HANDOFF.md` and stops. If the account resets within `drain.waitIfResetWithinMinutes`, the run waits. If only one model ran out, it goes on with the next in `drain.modelFallback`. Otherwise a session on another account continues from `HANDOFF.md`.

## Ask or auto

`handoff` in `fleet.json` decides: `auto` moves the run at once; `ask` posts one comment with the `flow handoff <id> --to <account>` command and waits for the reset. `flow handoff <id> --wait` keeps a run where it is.

## Caps

No new session starts while load per CPU is at `drain.maxLoadPerCpu` or above, or on an account with `drain.maxLivePerAccount` sessions. `drain.maxReviewRounds` reviews asking for changes park the run.

## Terminal or schedule

In a terminal, `flow drain` passes every `drain.pollSeconds` until nothing is left or Ctrl-C, which leaves sessions running. On a schedule, the `flow-drain` tick runs `flow drain --tick`.

## Parts

- `templates/drain/worker-brief.md` and `templates/drain/reviewer-brief.md`: what each session reads first.
- `flow watch`: wait on any PR by hand.
