# Draining in parallel

`flow drain --parallel 3` carries three ready items at once, each in its own worktree on the account with the most room. A separate reviewer reads every push; `flow pr` opens the PR only after a clean review at the branch head.

## Before you start

Allow each account flow may spend with `flow accounts set <id> --role rotation`; with none, sessions use your own login. Each user judges their own use of more than one account against Anthropic's terms.

## Where sessions run

`--host` picks `cli`, `cmux` or `dorkos`; `auto` tries them in the order cmux, DorkOS, CLI.

## What each line means

- `claimed on <account> (cli)`: a worker started.
- `reviewer started at 4be1c2d`: a push is under review.
- `sent review-findings`: the worker got the findings.
- `sent open-pr`: the review came back clean.
- `moved to <account>`: an account ran out, so the work moved.
- `parked: <reason>`: a person is needed; the item says why.

## What happens at a limit

Near a limit, the worker finishes its step, writes `HANDOFF.md` and stops. If the account resets within `drain.waitIfResetWithinMinutes`, the run waits. If only one model ran out, it goes on with the next in `drain.modelFallback`. Otherwise a session on another account continues from `HANDOFF.md`.

## Ask or auto

`handoff` in `fleet.json` decides: `auto` moves the run at once; `ask` posts one comment with the `flow handoff <id> --to <account>` command and waits for the reset. `flow handoff <id> --wait` keeps a run where it is.

## Caps

New sessions wait while load per CPU reaches `drain.maxLoadPerCpu` or an account has `drain.maxLivePerAccount` sessions. `drain.maxReviewRounds` rounds of changes park the run.

## Terminal or schedule

In a terminal, `flow drain` passes every `drain.pollSeconds` until nothing is left or Ctrl-C. On a schedule, the `flow-drain` tick runs `flow drain --tick`.

## Parts

- `templates/drain/worker-brief.md` and `templates/drain/reviewer-brief.md`: what each session reads first.
- `flow watch`: wait on any PR by hand.
