# Before flow arms a PR

Flow can turn on auto-merge for a pull request: `flow pr --arm`, `flow review --approve` when `gates.review.mergeOnApproval` is on, and the drain when it re-arms after a review. Every one of those asks flow's arm guard first. The guard only ever says no. It never arms anything itself, and never sets a status or a label.

## What it refuses

Flow doesn't arm a PR when:

- a required check failed or was cancelled. A check that is still running is fine, because GitHub waits for it;
- the PR's head isn't the commit that was reviewed, or no full commit SHA was recorded;
- it doesn't merge into `main`;
- it touches a security path and has no `security-reviewed` label;
- a release freeze is on;
- it comes from a fork;
- it's closed or a draft, carries `hold`, `do-not-merge`, `wip` or `blocked`, or a reviewer asked for changes.

Package manifests, lockfiles, build wrappers (`gradlew`, `mvnw`), toolchain files (`.cargo/config`, `rust-toolchain`) and `.agents/flow/config.json` are always security paths, matched in any case. Your repo adds its own in `land.securityPaths`.

A refused `flow pr --arm` still opens the PR, unarmed, and the drain asks again on later passes. A refused `flow review --approve` still posts your approval, and you merge the PR yourself. Both say why in `armRefused`. Name the whole commit in `--head`: a short SHA ships but arms nothing.

## Your own checks: `land.preArm`

`land.preArm` lists checks to run before arming, each only when the PR touches one of its paths. An entry either dispatches a GitHub workflow and waits for that one run, or runs a command. Prefer the workflow wherever your repo has CI. A command is the fallback for a repo without it. It runs in a fresh, clean checkout of the reviewed commit, made so nothing in your own checkout or git settings can change it. It has no installed dependencies, so point it at a committed script that installs them (and list that script as a security path). Its environment holds PATH, the locale, TMPDIR, TZ, TERM, `CI=true` and an empty scratch HOME, never your tokens:

```json
"land": {
  "preArm": [
    { "paths": ["apps/client/**"], "run": "bash scripts/ci/browser-tests.sh", "timeout": 20 },
    { "paths": ["apps/**"], "wait": "workflow", "workflow": "browser-shards.yml" }
  ]
}
```

These checks run only in the drain, because `flow pr` and `flow review` are stopped long before a browser suite finishes. When one applies, those commands leave the arm to the drain, which runs the checks and arms the PR once they pass. Outside the drain, you merge it yourself.

Flow reads `land.preArm` and `land.securityPaths` only from the committed config on `main`. A PR that changes them is still held to `main`'s version. Commands run with no shell. A workflow must take `sha` and `nonce` inputs, put the nonce in its `run-name`, and fail unless it checked out `sha`. `config/CONFIG.md` in the plugin has every field.

## The release freeze

```bash
flow freeze on --reason "cutting 1.4"   # arm nothing in this project until...
flow freeze off                         # ...the release is out
flow freeze                             # is a freeze on?
```

Have your release process turn it on before a release and off after. The freeze is kept on this computer, never committed.

## After the merge: the squash check

Once a PR has merged, flow checks that the squash commit on `main` is what a clean review saw. It passes only when merging the reviewed commit into the squash's parent gives exactly the squash's tree, which also covers `main` moving lines nearby. A matching patch-id is noted but never enough: it ignores whitespace and where a change sits. A conflict, any other difference, or a merge with no clean review fails. Flow then comments on the PR, naming its author and `land.securityPaths.reviewer`, with both trees and the files that differ. A check that couldn't run (a commit missing, say) is retried, then reported too. A shallow clone can't be squash-checked, and every merge there says so; `git fetch --unshallow` fixes it. The check needs git 2.44 or later. A git too old to merge safely fails. Flow reverts nothing. The drain runs the check by itself. Outside the drain, run `flow squash-check <id>`.

## What this is not

The guard is a rail for flow's own arms. Flow runs inside the agent, so the rules that hold for everyone belong on GitHub, as required checks and rulesets. The `security-reviewed` label is a person's signal and carries over to later pushes. A per-commit security approval belongs on GitHub too.
