# Before flow arms a PR

Flow turns on auto-merge with `flow pr --arm`, `flow sweep`, `flow review --approve` (with `gates.review.mergeOnApproval`) and the drain's re-arm. Each asks flow's arm guard first.

## What it refuses

Flow doesn't arm a PR when:

- a required check failed or was cancelled (GitHub waits for one still running);
- the head isn't the reviewed commit, or none was recorded;
- it targets a branch other than GitHub's default;
- it wouldn't squash: a queue must squash (flow passes no method flag); without a queue, the repo must allow `--squash`;
- it has no `security-reviewed` label a person added after the head arrived (your own approval needs it only on a security path, unless the drain arms it), or no such `security-deep-reviewed` on a `review:deep` PR. Read [the label guide](./security-label.mdx);
- a release freeze is on;
- it comes from a fork;
- it changes dependencies while another such PR is queued or armed;
- its labels are unreadable (`labels-unreadable`); an empty array means none;
- it's closed, a draft, held (`hold`, `do-not-merge`, `wip`, `blocked`), or a reviewer asked for changes.

Manifests, lockfiles, build wrappers (`gradlew`, `mvnw`), toolchains (`.cargo/config`, `rust-toolchain`), patches (any `patches/`) and `.agents/flow/config.json` count as security paths, any case, as does your own list in `land.securityPaths`.

A new PR has no label yet, so `flow pr --arm` opens it unarmed, and the drain asks again. A refused `flow review --approve` still posts your approval. Both say why in `armRefused` and `flow status`. Name the whole commit in `--head`: a short one arms nothing.

## Your own checks: `land.preArm`

`land.preArm` lists checks to run before arming, each only when the PR touches one of its paths. An entry either dispatches a GitHub workflow and waits for that one run, or runs a command. Prefer the workflow; a command is for a repo without CI. It runs in a clean checkout of the reviewed commit, so nothing in your checkout or git settings can change it. It has no installed dependencies, so point it at a committed script that installs them (and list that script as a security path). Its environment holds a fixed system PATH, the locale, TMPDIR, TZ, TERM, `CI=true` and an empty scratch HOME, never your tokens:

```json
"land": {
  "preArm": [
    { "paths": ["apps/client/**"], "run": "bash scripts/ci/browser-tests.sh", "timeout": 20 },
    { "paths": ["apps/**"], "wait": "workflow", "workflow": "browser-shards.yml" }
  ]
}
```

Only the drain runs these checks: `flow pr` and `flow review` are stopped long before a browser suite finishes, so when one applies they leave the arm to the drain. Outside the drain, you merge it yourself.

Flow reads `land.preArm` and `land.securityPaths` only from the committed config on the default branch. A PR that changes them is still held to that branch's version. Commands run with no shell. A workflow must take `sha` and `nonce` inputs, put the nonce in its `run-name`, and fail unless it checked out `sha`. `config/CONFIG.md` in the plugin has every field.

## The release freeze

```bash
flow freeze on --reason "cutting 1.4"   # arm nothing in this project until...
flow freeze off                         # ...the release is out
flow freeze                             # is a freeze on?
```

Have your release process turn it on, then off. It stays on this computer.

## After the merge: the squash check

Once a PR has merged, flow checks that the squash commit on the default branch is what a clean review saw. It passes only when merging the reviewed commit into the squash's parent gives exactly the squash's tree, including nearby branch changes. A matching patch-id is noted but never enough: it ignores whitespace and where a change sits. A conflict, any other difference, or a merge with no clean review fails. Flow then comments on the PR, naming its author and `land.securityPaths.reviewer`, with both trees and the files that differ. A check that couldn't run (a commit missing, say) is retried, then reported. A shallow clone or git older than 2.44 can't run it, and every merge says so, never a pass; `git fetch --unshallow` fixes the first. Flow reverts nothing. The drain runs the check by itself. Outside the drain, run `flow squash-check <id>`.

## What this is not

The guard is a rail for flow's own arms. Flow runs inside the agent, so the rules that hold for everyone belong on GitHub, as required checks and rulesets. On a solo repo, flow cannot distinguish your label from an agent using your login; you keep that promise.
